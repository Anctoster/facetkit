# arch-flow

Метод и команда агентов для архитектурных задач в Archicad: исходные тексты и растровые чертежи → проверенное описание здания → модель на нужных слоях → комплекты чертежей Projekt budowlany и Projekt wykonawczy в PDF и DWG → оценка сроков и рисков. Тот же журнал и те же правила, что в viz-flow и facetkit.

## Как это работает

1. Архитектор заполняет **карточку задачи** (`skills/arch-item/scripts/TASK-CARDS.md`) — пять видов: многовариантное эскизирование, модель по исходным материалам, комплект PB, комплект PW, сроки и риски.
2. Агент-дирижёр превращает карточку в **бриф** с критериями приёмки и задаёт все вопросы сразу. Архитектор утверждает бриф один раз.
3. **Чертежи читает один агент, один раз.** Результат — описание здания (`spec.json`): этажи, стены, проёмы, перекрытия, зоны; у каждого элемента слой, источник и уверенность. Всё, что прочитать не удалось, становится вопросом архитектору, а не догадкой. Пока вопрос открыт, ничего не строится.
4. **Модель строится из описания, а не из картинки** — процедурой через API Archicad, пакетами, и после каждого пакета считывается обратно и сверяется с описанием по количеству, слоям, размерам и площадям.
5. **Комплект чертежей** собирается по шаблону бюро и проверяется по перечню листов, который утвердил архитектор: полнота, нумерация, масштабы, форматы, DWG, штампы; для PW — связь каждого листа с листом PB.
6. Независимый инспектор заново прогоняет проверки; PASS без них журнал не принимает.

## Многовариантное эскизирование

Перед моделью и чертежами — три отдельных шага по порядку: **генплан → планировки → фасады**. На каждом агент предлагает три–пять вариантов, различающихся по идее, и записывает их геометрию и числа. Инструмент `variants.py` считает показатели из геометрии, проверяет каждый вариант по ограничениям, которые задал архитектор, убеждается, что варианты действительно разные, оценивает их по весам архитектора и отмечает те, которые ни один другой не превосходит по всем критериям. Вариант, нарушающий ограничение, показывается с пометкой, а не убирается. **Выбирает архитектор**; можно запросить ещё один круг. На этом шаге в Archicad ничего не строится: моделируется только выбранный вариант.

## Изменение модели: что оно затрагивает на самом деле

Файл проекта после каждого сохранения новый — это ничего не значит. Сравниваются не файлы, а **элементы**: два снимка модели (`ifc_read.py` из выгруженного IFC или процедура считывания через API) сопоставляются по GUID и идентификаторам. `model_diff.py` называет, что добавлено, удалено и изменено, какие помещения и этажи это затрагивает, какие листы нужно выпустить заново и — по таблице последствий бюро (`impact.example.json`, вы редактируете её под проект и смежников) — кому что перепроверить: «стена W5 укорочена → КР: несущая ли; ЭОМ: розетки на этой стене; отделка: раскладка плитки в помещении 0.01; ведомость дверей».

Дальше `archflow.py stale --from change.json` возвращает на проверку только те доказательства, чья область задета. Сдвиг перегородки на первом этаже не сбрасывает проверки второго; пересохранение без изменений не сбрасывает ничего. Для маршрута `revise` действует и обратное правило: изменилось что-то сверх объявленного в брифе — проверка `change.declared` не проходит.

## Проверка того, что получено и что отправляется

| Маршрут | Вопрос | Инструмент |
|---|---|---|
| `trace` | Отвечает ли комплект на ТЗ — пункт за пунктом — и нет ли в нём того, о чём не просили? | `trace.py`: ТЗ один раз режется на нумерованные пункты (вы утверждаете список), у каждого — место, где он выполнен; инструмент сам идёт туда и смотрит: лист есть, строка в ведомости есть, элемент в модели есть. «Подтверждено словом» показывается отдельно, с именем |
| `rules` | Проходит ли модель по числовым требованиям проекта? | `rules_check.py`: список требований ведёте вы — что измеряется, предел, пункт нормы, кто и когда подтвердил число. Неподтверждённое правило не засчитывается никогда |
| `change` | Что изменилось между двумя версиями модели (в том числе полученной от смежника)? | `model_diff.py` |
| `audit` | Годится ли модель в работу: слои, заполненность свойств, площади против ТЗ, ключи элементов | `model_audit.py` |
| `issue` | Можно ли отправлять эту папку? | `outbox_check.py`: рабочие файлы, внутренние пометки и рецензионные комментарии в PDF, DOCX и XLSX, пустые ячейки ведомостей, снятые с производства артикулы, площади в экспликации против модели |

## Чему можно верить

- **Результат проверки принимается только с квитанцией.** Каждый инструмент подписывает файл результата хешем собственного кода и входных файлов. Журнал не принимает «OK», набранное руками, и не принимает файл от изменённой копии инструмента.
- **«Ничего не изменилось» говорится только тогда, когда сравнение было полным.** Если в снимке нет положения или размеров элемента, результат — «не сравнивалось», а не «идентично» (`change.complete`, `bim.complete`).
- **Процедура для младшей модели закреплена по тексту.** Регистрация записывает в журнал хеш процедуры; изменённая процедура возвращается сборщику и инспектору.
- **Идентификатор задачи — только имя папки**; путь в свидетельстве не может указывать за пределы проверяемой папки.

- **Якорь вне папки проекта.** При закрытии каждой задачи журнал печатает строку `ANCHOR номер:хеш`. Она попадает в отчёт вам и в заметки проекта; позже `verify --anchor` покажет, не переписывали ли запись задним числом. Сама цепочка хешей этого не показывает — её можно пересчитать.
- **Список решений от вашего имени.** При закрытии печатается всё, что в задаче было утверждено, подписано, снято или продавлено, и кем. Строка, которую вы не узнаёте, — дефект.
- **Подписанные списки.** Результат проверки по нормам и сверки с ТЗ считается только против того текста списка, который подписан (`sign`); изменили список после подписи — подпишите снова.
- **После изменения ничего не выходит наружу, пока возвращённые проверки не повторены** — маршрут `issue` не открывается.
- **Чужой текст — данные.** ТЗ заказчика, имена в модели смежника, строки ведомостей печатаются очищенными и укороченными; текст, обращённый к читателю («отметь выполненным»), становится вопросом к вам.
- **«Не прочитано» отдельно от «не найдено».** Скан без текстового слоя, слишком большой архив — названы; удалённый в режиме правок текст, скрытые листы и имена в свойствах файла — прочитаны.

Чего это не даёт: квитанция и подпись доказывают, *какой код* и *какой текст* использованы, а не что они верны; имена в журнале вписывает тот, кто запускает команду, — поэтому они показываются вам, а не считаются доказательством; от того, кто владеет компьютером, журнал не защищён.

## Память объекта

`archflow.py memory add --where zone:0.07 --text "Потолок опущен на 150 мм из-за балки — встраиваемые светильники не ставить" --by <имя>` привязывает урок к месту: помещению, этажу, листу, узлу. Когда следующая задача касается этого места, дирижёр вызывает `memory recall` и вносит урок в бриф. Урок — подсказка, которую надо проверить, а не факт: если место с тех пор изменилось, он помечается STALE. Расплывчатые записи («аккуратнее с потолком») и текст, обращённый к читателю, инструмент не принимает. **Урок, записанный агентом, — только предложение:** в бриф он попадает после того, как вы его подтвердите (`memory confirm`); при закрытии задачи предложенные уроки показываются вам.

## Затраты и рентабельность

`archflow.py cost report` показывает по каждой задаче токены, машинное время и — когда записаны (`cost add --kind person --minutes …`) — часы людей; отдельной строкой — сколько стоили правки после приёмки и по какой причине: в брифе этого не было, новое пожелание заказчика, пропущенный дефект. `quality` показывает, после каких этапов приходят замечания.

## Почему это экономично

| Шаг | Модель | Почему |
|---|---|---|
| бриф, запуск процедур, считывание модели, публикация, расчёт сроков, проверка по цифрам | Haiku | механическая работа по готовым процедурам и инструментам |
| эскизные варианты | Sonnet | предложить разные идеи — работа суждения; сравнивает их инструмент |
| чтение чертежей | Sonnet | единственный шаг, где нужны зрение и суждение |
| написание процедуры, когда её ещё нет | Sonnet | один раз на проект; дальше процедуру запускает Haiku |
| проверка, где нужна картинка | Sonnet | один предпросмотр на лист |

Растр читается один раз; дальше все шаги работают с числами.

## Что проверяется инструментами

| Инструмент | Проверки |
|---|---|
| `variants.py` | варианты генплана, планировок, фасадов: показатели из геометрии, ограничения, различимость, оценка по весам |
| `model_spec.py` | масштаб каждого скана по написанным размерам, слои, этажи, стены, замкнутость контуров, проёмы, площади помещений, открытые вопросы |
| `spec_compare.py` | модель против описания: количество, слои, размеры, площади, программа помещений |
| `sheets_check.py` | комплект против перечня: полнота, нумерация, масштабы, размер страниц PDF, DWG, штампы, связь PW с PB |
| `schedule.py` | даты с уверенностью 50 / 80 / 95 %, вероятность срыва, критическая цепочка, меры с выигрышем в днях |
| `ifc_read.py` | файл IFC (2x3, 4) → снимок модели: элементы, этажи, слои, помещения, свойства и количества, **положение и поворот каждого элемента, отпечаток его формы**; все длины в метрах, в каких бы единицах ни был файл. Снимок сам сообщает, чего не прочитал: нечитаемые записи, классы без особого чтения (сохраняются как `other`, а не теряются) |
| `model_audit.py` | снимок сам по себе: ключи элементов, слои по плану слоёв, заполненность обязательных свойств, площади против ТЗ |
| `model_diff.py` | два снимка по GUID: что изменилось, какие помещения, листы и смежные разделы затронуты; изменилось ли только объявленное |
| `rules_check.py` | модель против списка числовых требований, подтверждённого проектантом; узкое место помещения, уклон, 2h+s считаются из геометрии |
| `trace.py` | комплект против ТЗ по пунктам; строки ведомостей, о которых ТЗ не просило |
| `outbox_check.py` | папка перед отправкой: рабочие файлы; непрочитанное; внутренние пометки, комментарии, непринятые правки, скрытый текст и листы; имена в свойствах файлов; ведомости |
| `safe.py`, `receipt.py` | общие для всех инструментов: обработка чужого текста и квитанции результатов |

## Окупаются ли агенты на ваших задачах

`archflow.py efficiency` отвечает по каждому типу задачи (оценка сроков, обмер, модель, комплект PB, комплект PW, правки, варианты) на вопросы, которые бюро задаёт, прежде чем доверить агентам больше работы:

| Что | Откуда |
|---|---|
| верно с первого раза; принято без замечаний | вердикты инспектора и ваша приёмка; с 80 %-ным интервалом |
| ваше время на задачу — на бриф, вопросы, превью, проверку, исправления | `spent <ЗАДАЧА> --minutes M --on review` — записываете вы |
| та же работа вручную | `hand <ЗАДАЧА> --hours H --by имя` — **до** старта агентов |
| сэкономлено на задачу | ручная оценка минус ваше время; медиана и сумма |
| время работы агентов, токены, стоимость | журнал; цены — `"prices": {"sonnet": 3.0, "haiku": 0.8}` в `project.json` (за миллион токенов) |
| вопросы к вам, круги превью, изменённые брифы | журнал |
| что поймали проверки до того, как вы увидели результат | проверки, упавшие в прогоне инспектора |
| какой агент на какой модели возвращается на доработку; не справится ли модель дешевле | возвраты инспектора по паре «агент + модель» |

```
archflow.py efficiency                    # по-английски
archflow.py efficiency --lang ru          # или pl
archflow.py efficiency --html eff.html    # страница для бюро
archflow.py efficiency --json             # для своих таблиц
```

Честные ограничения, которые отчёт пишет сам:
- Оценка ручной работы, данная после старта агентов, показывается, но в экономию не входит: зная результат, оценивают иначе. Первая оценка не меняется.
- Нет записи вашего времени или ручной оценки — экономия «неизвестно», а не догадка.
- Меньше 5 задач — «слишком мало задач для вывода»; модели сравниваются, только когда у обеих не меньше 5 задач и интервалы не пересекаются.
- Дефекты, о которых никто не сообщил, и неучтённое время в отчёт не попадают.

## Чего метод не делает

- **Не хранит норм и не подтверждает соответствие им.** `rules.example.json` — пример формата с числами-заглушками; значения, пункт нормы и подпись вносит проектант. Инсоляция и другие расчёты, для которых нужна геометрия окружения, в метод не входят.
- **Не ищет коллизии.** Снимок не содержит геометрии; пересечения элементов проверяются штатным обнаружением коллизий Archicad, а его результат записывается как обычная проверка.
- **Не подтверждает соответствие составу комплекта по нормам.** `sheets.pb.json` и `sheets.pw.json` — стартовые перечни, а не текст rozporządzenia. Состав комплекта и его соответствие действующим требованиям утверждает проектант; дата проверки записывается в `project.json`.
- **Не принимает проектных решений.** Толщины, составы, расхождения между чертежами — вопросы архитектору.
- Процедуры для Archicad в плагин не входят: их пишет `arch-builder` при первом запуске на проекте, под команды установленного API, и проверяет инструментами.

Тесты без Archicad: `python3 -m unittest discover -s tests`.
